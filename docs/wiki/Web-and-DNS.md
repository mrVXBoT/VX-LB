# وب و تونل DNS

این گروه WS، HTTP CONNECT، HTTPS CONNECT و Slipstream را در کنار هم نشان می‌دهد ولی نیازمندی آن‌ها متفاوت است. HTTP/HTTPS فعلی مسیر CONNECT با کانال دادهٔ دارای احراز هویت متقابل است؛ این نام‌ها به معنی پشتیبانی XHTTP، HTTP/2 عمومی یا HTTP/3 نیستند.

## Slipstream و delegation واقعی

یک زیردامنه مثل `tunnel.example.com` را به نام DNS authoritative خودتان، مثلاً `ns1.example.com`، واگذار کنید؛ NS به hostname اشاره می‌کند و رکورد A/AAAA آن hostname باید به سرور خارج برسد. برای nameserver داخل همان زیردامنه، نیاز glue را در DNS والد بررسی کنید. فقط ساخت رکورد A برای tunnel کافی نیست.

فرم شامل دامنه، resolverهای کاماجدا با پورت مثل `1.1.1.1:53,8.8.8.8:53`، پورت DNS خارج (پیش‌فرض 53) و QPS هر IP منبع از 10 تا 2000 (پیش‌فرض 1000) است. resolver عمومی برای delegation معمول به پورت 53 نیاز دارد؛ پورت دلخواه برای resolver مستقیم/سفارشی است. UDP پورت موردنظر، DNS delegation و سرور authoritative باید در مسیر قابل دسترسی باشند.

محدودیت نرخ روی UDP همان استخر اعمال می‌شود و burst دوثانیه‌ای دارد؛ کاربران پشت یک resolver ممکن است سقف منبع مشترک داشته باشند. این حامل برای fallback است و سرعت عمومی اینترنت را تضمین نمی‌کند. تغییر دامنه/resolver/QPS از تنظیمات اختصاصی استخر انجام می‌شود؛ شکست باید نتیجه و بازگردانی را نشان دهد. خانواده آزمایشی است و پذیرش عمومی DNS و سرورهای مستقل نیاز به آزمون واقعی دارد.

## HTTP و HTTPS

کانفیگ و گواهی اختصاصی توسط مسیر مدیریت‌شده تولید می‌شوند. HTTP CONNECT نیز کانال دادهٔ احرازشده دارد؛ صرف ظاهر HTTP نباید با رلهٔ بی‌احراز هویت اشتباه شود. HTTP↔HTTPS مسیر تغییر اختصاصی و آزمون داده دارد. برای CDN، پشتیبانی واقعی CONNECT و نوع ترافیک را بررسی کنید؛ فعال‌کردن Proxy عادی Cloudflare تضمین عبور نیست.

## انتخاب و اجرای این خانواده

در «استخرها ← استخر جدید» خانواده و گزینهٔ پایین را انتخاب کنید، فیلدهای مرتبط را کامل و پورت سرویس کاربران را مشخص کنید. ثبت درخواست را از نتیجهٔ نهایی جدا بدانید. بعد از استقرار، نودها و سرویس واقعی را بررسی کنید؛ [شروع سریع](Quickstart.md) و [عملیات و بازیابی](Pools-and-Operations.md) روند مشترک را توضیح می‌دهند.

نام‌های زیر عین گزینه‌های کد هستند. شناسهٔ transport، mode و profile در صورت تفاوت جدا نوشته شده‌اند.

## WebSocket (WS)

<!-- profile:other:ws:default -->

شناسهٔ انتقال: `ws`.

انتقال WebSocket بدون TLS؛ برای استفاده پشت پراکسی معکوس باید مسیر و پورت‌ها هماهنگ باشند.

WebSocket خام بدون TLS؛ استفاده پشت reverse proxy به مسیر، Upgrade و امنیت پراکسی وابسته است.

## HTTP CONNECT

<!-- profile:other:http:default -->

شناسهٔ انتقال: `http`.

حامل HTTP/1.1 CONNECT با انتقال TCP و UDP در کانال دارای احراز هویت دوطرفهٔ TLS.

حامل HTTP/1.1 CONNECT با کانال داده احرازشده؛ CONNECT مسدود یا تغییر هدر نامناسب در پراکسی می‌تواند مسیر را بشکند.

## HTTPS CONNECT

<!-- profile:other:https:default -->

شناسهٔ انتقال: `https`.

حامل HTTPS CONNECT روی TLS 1.3 با احراز هویت دوطرفه و گواهی اختصاصی.

CONNECT بر TLS/mTLS؛ زمان سیستم، اعتماد گواهی و مسیر واقعی حامل را کنترل کنید.

## Slipstream (DNS)

<!-- profile:other:slipstream:default -->

شناسهٔ انتقال: `slipstream`.

تونل پشتیبان روی پرس‌وجوهای DNS؛ نیازمند واگذاری زیردامنه و تنظیم resolver و محدودیت نرخ.

مناسب fallback آزمایشی؛ ابتدا delegation عمومی و پاسخ DNS را مستقل از پنل بررسی کنید، سپس resolver و QPS را تنظیم کنید.

## اگر ساخت یا ارتباط شکست خورد

برای وب، تطبیق حامل/گواهی/پراکسی؛ برای DNS، NS والد، A/AAAA میزبان nameserver، UDP:53، resolver و نرخ مشترک منبع را بررسی کنید.

ابتدا متن خطا و آخرین مرحله را بخوانید؛ اگر درخواست timeout شده، وضعیت را دوباره بگیرید تا نتیجهٔ نامشخص با اجرای دوباره اشتباه نشود. در حذف ناموفق ابتدا دسترسی را اصلاح و حذف عادی را تکرار کنید.
